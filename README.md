# notion-project-logger

> Notion "프로젝트 관리 템플릿" 기반 프로젝트에서 업무 등록·진행 관리·완료 정리·작업 일지를 대신 맡는 Claude 스킬

이 템플릿은 **업무 DB 하나 + 업무 로그 DB 하나 + 자료실 폴더 구조**로 이루어져 있고, 새 팀 프로젝트마다 복제해서 씁니다. 복제본마다 데이터베이스 ID는 새로 생기지만 속성 이름과 선택지, 페이지 본문 구조는 같습니다. 이 스킬은 그 구조를 알고 있는 팀원처럼 동작합니다.

## 요구 사항

- **Claude** — Cowork, Claude Code, 또는 Agent SDK
- **Notion MCP 연결** — 페이지 조회·생성·수정 권한
- **대상 프로젝트** — 위 템플릿으로 만든 Notion 프로젝트. 업무 DB에 `이름` / `진행 상황` / `날짜` 속성이 있어야 합니다

> 이 스킬은 **위 템플릿 구조 전용**입니다. 구조가 다른 Notion 워크스페이스를 자동으로 인식하거나 맞춰주지 않습니다. 스키마가 맞지 않으면 규칙을 억지로 적용하지 않고 그 사실을 알리고 멈춥니다.

## 설치

**Cowork** — `.skill` 파일(이 폴더를 압축한 것)을 열고 "스킬 저장"을 누릅니다.

**Claude Code / Agent SDK** — 이 폴더를 스킬 디렉터리에 복사합니다.

```bash
git clone https://github.com/tacocat404/notion-project-logger.git
```

## 사용법

이름을 부르지 않아도 됩니다. 업무를 추가하거나, 상태를 옮기거나, 일을 마무리하거나, 대화를 기록하거나, 새 프로젝트를 시작할 때 스킬이 알아서 나섭니다. "Notion"이라는 단어가 나오지 않아도, 데이터베이스 ID가 다른 새 복제본이어도 동작합니다.

```
"로그인 API 구현 업무 등록해줘"
"그거 지금 막혔어, 서버 응답을 기다리는 중이야"
"다 했어, 정리해줘"
```

## 워크플로

| # | 이름 | 하는 일 |
|---|---|---|
| 1 | 업무 등록 | 동사형 이름·진행 상황·날짜를 갖춰 업무 생성. 2주 넘을 일은 분할 제안 |
| 2 | 진행 중 업무 수정 | 진행 메모 / 진행 상황 / 업무 로그 세 갈래를 구분해 기록 |
| 3 | 완료 의식 | 결과 & 인사이트 → 산출물 정리 → 상태 변경 → 체크박스, 네 단계 전부 |
| 4 | 새 프로젝트 세팅 | 팀원별 개인 폴더 생성, 초기 업무 등록 |
| 5 | 개인 작업 일지 | 개인 자료실 폴더에 서술형 작업 기록. 체크포인트에 모아서 작성 |
| 6 | 스냅샷 드리프트 점검 | 주 1회 GitHub 사본과 실행 중인 스킬의 차이를 확인해 **보고만** |

## 동작 원칙

**ID를 하드코딩하지 않습니다.** 복제본마다 데이터베이스 ID가 다르므로, 매번 해당 프로젝트의 실제 데이터베이스를 조회합니다. `references/notion-schema.md`의 ID는 전부 자리표시자입니다.

**가이드 페이지를 매번 읽습니다.** 요약본을 캐시해두고 쓰지 않습니다. 팀이 진행하면서 자기네 가이드를 고치기 때문에, 그 프로젝트의 살아 있는 가이드가 항상 기준입니다. (대화당 프로젝트별 1회만 조회하고 그 세션 동안 재사용합니다.)

**개인의 판단을 대신 쓰지 않습니다.** 결과 & 인사이트, 회고, "오늘 배운점" 같은 본인 성찰 항목은 지어내지 않습니다. 초안을 제안하는 선까지만 하고 본인 확인을 받습니다. 반면 대화에서 실제로 일어난 일의 기록은 확인 없이 바로 적습니다 — 그 둘은 다릅니다.

**남의 업무를 건드리지 않습니다.** 다른 사람이 담당인 업무의 진행 상황은 바꾸지 않고 댓글을 남깁니다.

**스스로를 덮어쓰지 않습니다.** Workflow 6은 차이를 알려줄 뿐, 원격에서 받아온 내용으로 스킬을 자동 갱신하지 않습니다. 이유는 아래에.

## 이 저장소의 위치

**이 저장소는 백업·공유용 스냅샷이지 진실의 기준이 아닙니다.** 실제로 실행되는 것은 계정에 저장된 스킬이고, 그건 대화 중에 직접 수정됩니다. 따라서 이 저장소는 마지막으로 push한 시점까지만 최신입니다.

초기 버전에는 GitHub를 기준으로 스킬을 자동 갱신하는 기능이 있었습니다. 방향이 거꾸로였습니다 — 저장소가 뒤처져 있을 때 최근 작업을 조용히 지워버리는 구조였고, 실제로 그 직전까지 갔습니다. Workflow 6의 수정본이 저장소에만 2시간 존재하는 동안 다른 대화가 옛 버전을 기준으로 계정 사본을 고쳤고, 어느 방향으로든 통째로 복사했다면 한쪽 작업이 사라졌을 상황이었습니다.

그래서 지금은 **알림만** 합니다. 동기화는 사람이 판단합니다.

## 저장소 구조

```
notion-project-logger/
├── SKILL.md                        스킬 정의 — 이름, 실행 조건, 워크플로 1~6
├── README.md
└── references/
    ├── notion-schema.md            템플릿 공통 속성/타입 구조 (ID는 자리표시자)
    └── template-rules.md           공식 가이드 규칙 요약 — 대비용
```

`references/template-rules.md`는 **대비용**입니다. 프로젝트의 실제 가이드 페이지를 찾을 수 없을 때만 쓰고, 그 경우 사용자에게 알립니다.

## 만들게 된 계기

팀 프로젝트에 관리 템플릿과 가이드를 만들어두어도, 팀원들이 그걸 그대로 따르게 만드는 건 다른 문제였습니다. 규칙을 지키라고 계속 상기시키는 대신 **행정적인 기록을 대신 처리해주는 쪽**으로 방향을 잡은 것이 이 스킬의 출발점입니다. 팀원들이 대화하며 일하는 동안, 누가 무엇을 하고 있는지가 따로 묻지 않아도 드러나게 하는 것이 목표였습니다.

Claude 스킬은 **재사용 가능한 작업 매뉴얼**에 가깝고, 필요한 만큼만 단계적으로 읽히는 구조입니다 — 이름과 설명은 항상, 본문은 호출될 때, `references/`는 실제로 그 내용이 필요할 때. 그래서 판단 기준은 `SKILL.md` 본문에, 상세한 스키마와 규칙 요약은 참고 파일로 나눠 담았습니다.

여섯 개 워크플로는 한 번에 나오지 않았고, 실제 워크스페이스에서 업무를 등록하고 수정하고 보류했다가 재개하고 완료 처리하는 흐름을 돌려보며 다듬었습니다. 그 중 가장 크게 뒤집은 것이 Workflow 6입니다. 처음에는 GitHub 내용으로 스킬을 **자동 갱신**하게 해두었는데, 저장소가 뒤처져 있을 때 새로 만든 기능을 그대로 지워버릴 뻔했습니다. 그 뒤로 자동 덮어쓰기를 걷어내고 차이를 보여주기만 하도록 바꿨습니다. (위 [이 저장소의 위치](#이-저장소의-위치) 참고)
